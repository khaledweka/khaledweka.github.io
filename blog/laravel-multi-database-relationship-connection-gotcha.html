Laravel Multi-DB Relationship Gotcha: Why Eager Loads Hit the Wrong Database

August 5, 2026

Share 𝕏

Ever spent 1.5 hours debugging a query hitting the wrong database? I did.

In a multi-connection Laravel app, I had two models: Order on a dedicated connection (secondary_mysql), and OrderMeta with no explicit connection, expecting it to use the app default (mysql). 

Order::with('orderMeta')->first();

Laravel executed the OrderMeta query on secondary_mysql. The table was not there. Boom.

Why this happens

During relationship resolution, if the related model does not define $connection, Eloquent can inherit the parent model's connection in that relationship context.

Chart 1: Relationship connection resolution flow

Order (secondary_mysql) → with('orderMeta') → OrderMeta has no $connection → inherits secondary_mysql
Result: query wrong DB → table not found

This behavior is by design. Laravel assumes related data usually lives in the same database as the parent model. Good default in many cases — dangerous in split-database domains.

The one-line fix

class OrderMeta extends Model
{
    protected $connection = 'mysql';
}

Explicit beats implicit. Always.

Chart 2: Risk before vs after explicit connection

Implicit model
Explicit model

Illustrative engineering-risk score for accidental wrong-DB reads in eager-loaded relationships.

Testing impact (important)

Once you hardcode $connection, that model no longer follows test-level default connection overrides. If your suite relies on in-memory SQLite by switching the default connection, this model can still target mysql unless explicitly configured.

Chart 3: Test impact matrix after hardcoding $connection

Area Impact Action
Default connection override in tests High Review test assumptions; explicit model connection bypasses default override.
Connection config in test env High Define mysql (or mapped alias) in test configuration.
Migrations and seeders Medium Ensure schema for explicit connection exists before tests run.
Feature tests not touching this model Low No change needed unless relationship path is exercised.

Pre-merge checklist

  • Ensure the test environment has the explicit connection configured.
  • Run migrations against that connection too.
  • Audit tests that used default-connection overrides — they no longer affect this model.

Takeaway

Multi-database Laravel apps are straightforward until relationship resolution silently rewires connections. If a model belongs to a specific database, declare it explicitly — and align test infra with that decision.
